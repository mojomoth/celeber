# 개발 도구 사용법

PROMPT_V0이 지정한 도구 6개를 원문으로 확인하고, 이 프로젝트에서 쓰는 방법만 정리했다. 원문 확인일은 2026-11-24이다.

## 설치 위치와 호출

플러그인(`/plugin install`)과 `npx skills add -g`는 사용자 전역 설정(`~/.claude`)을 바꾸므로 쓰지 않았다. 원본 저장소의 skill 파일을 프로젝트 `.claude/skills/`에 그대로 복사했다.

| 도구 | 위치 | 원본 커밋 |
|---|---|---|
| fluent-korean | `.claude/skills/fluent-korean/` (output-style 본문을 skill로 감쌈, 본문은 원문 그대로) | ce8683f |
| ponytail | `.claude/skills/ponytail/`, `ponytail-review/`, `ponytail-audit/` | ebd8654 |
| no-ai-slop | `.claude/skills/no-ai-slop/` (SKILL.md, eval.md) | 000650b |
| hallmark | `.claude/skills/hallmark/` (SKILL.md, references, scripts) | 04977e1 |
| gauntlet-loop | `.claude/skills/gauntlet-loop/` | 9b1975a |
| LLM Wiki | 설치 없음. 패턴 문서 | gist |

- Claude CLI는 프로젝트 루트에서 실행하면 위 skill을 자동으로 읽는다. 이름으로 호출한다(`/ponytail-review`, `/no-ai-slop`, `/hallmark audit <경로>`).
- Codex CLI는 `.claude/skills/`를 읽지 않는다. Codex에 보내는 프롬프트에는 아래 체크리스트를 직접 붙인다.
- ponytail의 훅(상태 표시줄, 하위 에이전트 자동 주입)은 설치하지 않았다. 항상 켜져 있지 않으므로 필요할 때 호출하거나 체크리스트를 붙인다.

## fluent-korean

- 출처: https://github.com/snflkd/fluent-korean (`plugins/fluent-korean/output-styles/fluent-korean.md`)
- 하는 일: 조사·어미·문장 성분이 빠진 기계식 한국어를 막고, 의미가 분명한 문장을 쓰게 한다.
- 언제: 앱 메뉴·설명·대사, AI 분석 결과 문구, run.md·report.md·wiki, 하위 에이전트에게 보내는 한국어 프롬프트. 원작자는 요약본보다 원문 전체를 넣으라고 권한다. Claude 에이전트는 skill을 읽게 하고, Codex에는 SKILL.md 본문을 붙인다. 아래 체크리스트는 검증용이다.

체크리스트
1. 의미가 있는 문장 성분을 생략하지 않는다. '~의'를 겹쳐 쓰면 성분이 빠지기 쉬우니 풀어 쓴다.
2. 문장은 서술어와 종결어미로 끝낸다. 명사구나 연결어미로 끝내지 않는다(제목과 목록은 예외).
3. 조사와 어미를 생략하지 않는다. 전보문처럼 명사만 나열하지 않는다.
4. 맥락에 맞는 한자어를 쓰고, 조사와 어미로 어휘 사이의 관계를 드러낸다.
5. 일반 어휘 자리에 비유적 어휘를 쓰지 않는다(박다, 얹다, 치우다, 흐름).
6. 엠대시(—)를 쓰지 않는다. 콜론이나 접속사로 바꾼다.
7. 코드, 변수명, 주석, 커밋 메시지, 로그는 프로젝트 관례를 따르고 이 지침을 적용하지 않는다.
8. 기술 용어는 정착된 번역어나 음차를 쓰고, 없으면 원어를 쓴다. 영어로 쓸 것을 억지로 번역하지 않는다.
9. 하위 에이전트에 한국어 프롬프트를 보내기 전과 결과를 전달하기 전에 위 항목을 점검한다.

## ponytail

- 출처: https://github.com/DietrichGebert/ponytail (`skills/ponytail/SKILL.md`, `AGENTS.md`)
- 하는 일: 과제를 끝까지 해결하는 가장 작은 변경을 고르게 하고, 필요 없는 코드와 추상화를 막는다.
- 언제: 모든 코드 작업. Gate 1에서 PoC를 고칠 때, Gate 2에서 PoC 코드를 다시 쓰지 않고 통합할 때, Gate 3에서 불필요한 코드를 지울 때. 커밋 전에는 `/ponytail-review`, 게이트 마감 전에는 `/ponytail-audit`를 돌린다(둘 다 보고만 하고 코드를 바꾸지 않는다).

체크리스트
1. 먼저 과제와 관련 코드를 읽고 변경이 닿는 곳(호출부, 테스트, 픽스처, 설정, export)을 모두 적는다.
2. 다음 순서에서 처음으로 통하는 방법을 쓴다: 꼭 필요한가 → 이미 코드베이스에 있는가(`pocs/core`, `@celeber/ui`) → 표준 라이브러리·플랫폼 기능 → 설치된 의존성 → 한 줄 → 동작하는 최소 코드.
3. 요청받지 않은 추상화, 래퍼, 옵션, 설정, "나중을 위한" 코드를 만들지 않는다. 몇 줄 때문에 의존성을 추가하지 않는다.
4. 기존 구조(레이어, 인터페이스, 관례)를 유지한다. 추가보다 삭제를 우선한다.
5. 버그는 호출부를 모두 grep한 뒤 공용 코드에서 원인을 한 번에 고친다.
6. 분기, 루프, 파서, 보안이 있는 새 로직에는 작은 테스트나 assert 하나를 남긴다.
7. 알고 남긴 한계는 `shortcut: <한계>, <언제 고칠지>` 주석으로 표시한다.
8. 절대 줄이지 않는다: 신뢰 경계의 입력 검증, 데이터 손실을 막는 오류 처리, 보안(API 키는 서버에만), 접근성, 요청받은 기능.
9. 답의 마지막 1~2줄에 생략했거나 확인하지 못한 것과 위험을 적는다.

## no-ai-slop

- 출처: https://github.com/petergyang/no-ai-slop (`skills/no-ai-slop/SKILL.md`, `eval.md`)
- 하는 일: 글쓴이의 목소리는 지키면서 AI가 자주 쓰는 상투 패턴을 찾아 고친다. 영어 기준이라 아래는 한국어에 맞게 옮긴 것이다.
- 언제: 랜딩 문구, 분석 결과 리포트 문장, 퍼스널컬러·추구미 생성 프롬프트에 넣을 금지 규칙, 문서 검토. 검사만 할 때는 "is this slop?" 모드로 해당 줄을 인용하고 고칠 방향만 적는다.

체크리스트
1. "X가 아니라 Y입니다" 같은 이분법 대조를 쓰지 않는다. Y를 바로 말한다.
2. 서두 군말("결론부터 말하면", "중요한 점은", "솔직히")과 가짜 통찰("아무도 말해주지 않는")을 지운다.
3. 중요성 과장(혁신적, 획기적, 완벽한, 한 차원 높은)과 출처 없는 권위("전문가들은", "연구에 따르면")를 쓰지 않는다. 사실과 출처로 바꾸거나 지운다.
4. "~를 보여줍니다", "~를 강조합니다"처럼 의미를 덧씌우는 꼬리 구절을 지운다.
5. 같은 대상을 다른 단어로 돌려 부르지 않는다. 맞는 단어를 반복한다.
6. 극적인 단문 나열, 콜론으로 터뜨리는 문장, 요약을 되풀이하는 결말, 멋을 낸 마지막 한 줄을 지운다.
7. 이식성 검사: 다른 사람·제품에 그대로 옮겨도 말이 되는 문장은 지우거나 구체적인 값(색, 수치, 부위)으로 바꾼다.
8. 형식 장식을 빼낸다: 제목 이모지, 문장 중간 굵은 글씨, 두 문장이면 될 목록.
9. 없는 주장, 예시, 수치를 지어내지 않는다.

## hallmark

- 출처: https://github.com/Nutlope/hallmark (`skills/hallmark/SKILL.md`, `references/flow.md` § App screens)
- 하는 일: 생성형 UI의 상투적인 디자인을 막는 하한선(Floor)과 린터(`sloplint`)를 제공한다.
- 언제: UI 목업은 현재 HOLD라 새 화면을 Hallmark로 만들지 않는다. 기존 디자인에는 이름을 붙여 부를 때만 쓴다. Gate 2·3에서 `/hallmark audit <경로>`로 보고만 받고, 고칠지는 사람이 정한다. 디자인 시스템은 `@celeber/ui`의 토큰이 기준이며 Hallmark 테마로 바꾸지 않는다.
- 린트: `node .claude/skills/hallmark/scripts/sloplint.mjs <경로> --scope app` (.html, .css, .tsx를 읽는다). 정적 검사는 동작을 확인했다. `--render`와 `--url http://localhost:310x`는 puppeteer-core가 필요한데 아직 설치하지 않았다. 20번(Hallmark 스탬프) FAIL은 Hallmark가 만든 페이지가 아니므로 이 프로젝트에서는 무시한다.

체크리스트
1. 모든 색과 글꼴은 `:root` 토큰을 거친다. 토큰 밖에 색 리터럴이나 `font-family`를 쓰지 않는다.
2. `transition: all`을 쓰지 않는다. width, height, top, left를 애니메이션하지 않는다(transform, opacity만).
3. `html`, `body`에 `overflow-x: clip`. `hidden`이나 `100vw`를 쓰지 않는다.
4. 모든 조작 요소에 `:focus-visible`. 모든 애니메이션에 `prefers-reduced-motion` 대안.
5. 지어낸 수치, 후기, 로고, 사례 수를 넣지 않는다.
6. 아이브로(제목 위 작은 라벨), 자간 넓힌 대문자 라벨, 가운뎃점으로 이은 메타 문자열, 장식용 상태 점을 쓰지 않는다.
7. 보라→파랑 그라디언트, 카드 안의 카드, 아이콘 대신 이모지를 쓰지 않는다.
8. 데이터를 불러오는 영역은 로딩·빈 상태·오류·정상 네 가지 상태를 모두 그린다.
9. 강조색은 주요 동작, 현재 선택, 상태에만 쓴다. 조작 요소는 터치 영역 44px 이상.
10. 기존 화면을 다듬을 때는 재료(토큰, 색, 글꼴, 상태, 대비)만 고치고 구조는 바꾸지 않는다. 구조 문제는 목록으로만 보고한다.

## gauntlet-loop

- 출처: https://github.com/robonuggets/gauntlet-loop (`.claude/skills/gauntlet-loop/SKILL.md`). 기법 원작자는 Matt Shumer.
- 하는 일: 실제로 존재하는 기준물(bar)을 정하고, 구현자와 별도의 엄격한 검증자가 블라인드 비교에서 이길 때까지 반복하게 하는 프롬프트를 만든다.
- 언제: 모든 게이트의 Plan → Build → Independent Critic → Fix → Recheck. 화면은 `docs/ui/`의 제공 디자인과 캐릭터 원본이 bar다. PoC·API는 POC.md의 기대 입출력과 실제 호출 결과가 bar이고, 응답 시간·성공률 같은 측정값을 함께 둔다.

체크리스트
1. bar는 이름이 있고, 검증자가 직접 열 수 있고, 나란히 놓고 고를 수 있어야 한다. 막연한 기준은 bar가 아니다.
2. 작업을 따로 판단할 수 있는 가장 작은 단위로 나눈다.
3. 단위마다 구현자와 검증자를 분리한다. 검증자는 새 컨텍스트에서 시작하고 구현자의 설명을 근거로 삼지 않는다.
4. 검증자는 실제 산출물(실행 화면 스크린샷, 실제 API 응답)을 열어 bar와 라벨을 지운 채 비교한다.
5. 점수 대신 "어느 쪽이 나은가"를 고르고, 남은 가장 큰 차이 하나를 구현자에게 돌려준다. 칭찬은 쓰지 않는다.
6. 종료 조건은 우리 결과가 이기거나 사람이 멈출 때다. 반복 횟수로 끝내지 않는다. bar를 얻을 수 없으면(키 오류, 원본 없음) run.md에 BLOCKED로 적고 멈춘다.
7. 프롬프트는 120~180단어(영문 기준) 정도의 문단 하나로 짧게 쓰고, 구조·파일 배치·반복 횟수를 미리 정하지 않는다.
8. `/loop`, `ultracode`는 Claude Code 전용이다. Codex에는 "검증자가 우리 쪽을 고를 때까지 반복한다. 구현자와 검증자는 별도 에이전트로 돌린다"로 바꿔 쓴다.
9. HIL 단계에서는 사람의 판정이 마지막이다.

## LLM Wiki (Karpathy)

- 출처: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f
- 하는 일: LLM이 원본 자료를 읽고 상호 링크된 마크다운 위키를 계속 갱신하게 하는 패턴이다.
- 언제: `docs/wiki/`를 관리할 때. 원본은 `docs/POC.md`, `docs/prompts/`, `docs/ui/`, `assets/`, 위키는 `docs/wiki/`, 규칙(schema)은 `CLAUDE.md`·`AGENTS.md`가 맡는다.

체크리스트
1. 원본 자료는 읽기만 하고 고치지 않는다. 위키는 LLM이 쓴다.
2. 자료를 반영(ingest)할 때: 원본을 읽고 → 관련 위키 문서를 고치고 → index.md를 갱신하고 → log.md에 항목을 추가한다.
3. index.md는 내용 목록이다. 문서마다 링크와 한 줄 요약을 분류별로 적는다. 질문에 답할 때는 index.md부터 읽는다.
4. log.md는 시간순으로 덧붙이기만 한다. 항목은 `## [YYYY-MM-DD] ingest|create|change|fix|verify|lint | 제목` 형식으로 시작해 grep으로 찾을 수 있게 한다.
5. 같은 내용을 여러 문서에 복사하지 않는다. 출처 문서로 링크한다.
6. 새 자료가 기존 내용과 어긋나면 해당 문서에 표시하고 고친다.
7. 주기적으로 점검(lint)한다: 문서 간 모순, 낡은 주장, 링크가 없는 문서, 빠진 교차 링크.
8. 쓸모 있는 답이나 비교 결과는 채팅에 두지 않고 필요한 경우에만 위키 문서로 남긴다. 이 프로젝트는 index.md, log.md, 실제 필요한 문서만 둔다.
